# План миграции: RPi (CBS) + ATmega как HAL

Документ фиксирует **целевую архитектуру**, **разрыв с текущей реализацией** и **пошаговый план работ** по переносу бизнес-логики и кинематики с монолитного Arduino-скетча на клиент Python/PyQt5 на Raspberry Pi. ATmega остаётся исполнителем физики по утверждённому Serial-протоколу.

Связанные материалы: [hardware_barcode_relay_dispensing.md](hardware_barcode_relay_dispensing.md), [client_components_description.md](client_components_description.md).

---

## 1. Цель и принципы

| Цель | Формулировка |
|------|----------------|
| Разделение ролей | RPi — дирижёр: БД, FSM/UI, последовательность выдачи, таймеры UX; ATmega — HAL: моторы, замки, свет, опрос датчиков. |
| Координаты | Физические **X/Z в миллиметрах** хранятся в БД (или конфиге), а не в `PROGMEM` (`COORD.h`). |
| Безопасность замка | Открытие через **`$LOCK,ms`** на контроллере (fail-safe по времени), без рассинхрона с «зависшей» малиной. |
| Протокол | Линии текста, 9600 baud, завершение `\n`|

## 2. Снимок текущей реализации (от чего отталкиваемся)

### 2.1. Два SerialManager

Как описано в [hardware_barcode_relay_dispensing.md](hardware_barcode_relay_dispensing.md): в `main.py` создаются два экземпляра [serial_manager.py](../client/BarcodeScanner/serial_manager.py) — контроллер выдачи и сканер. Один класс обслуживает **разные** протоколы; важно не перепутать порты в `config.json`.

### 2.2. Протокол «номер ячейки»

- Отправка: [action_cmd.py](../client/EventsSystem/action_cmd.py) — `cmd_send` вызывает `controller_serial_manager.send_data(number)`, что даёт строку `$<номер>\r\n` (см. `send_data` в `serial_manager.py`).
- Приём: `raw_read_data()` ожидает кадр вида `$…\n`, внутри **только цифры** `1`/`2` → сигналы `command_is_send` / `command_ok`.
- FSM: `cmd_send` → `command_is_send` → `screen_32_wait` → `command_ok` → `write_db_tool_consumption` → `screen_11_tool_issued` ([state_map.py](../client/StateMachine/state_map.py)).

### 2.3. Несогласованности, которые миграция должна устранить

1. **Потокобезопасность записи в COM:** `send_data` вызывается из контекста действий FSM (фактически GUI-поток), тогда как чтение идёт в потоке `SerialManager.run()`. Для нового протокола с частыми командами и очередями нужна **единая очередь отправки** в потоке порта (или явный mutex вокруг `serial_conn.write`).
2. **Два пути отправки:** в [Executor.py](../client/EventsSystem/Executor.py) есть `cmd_send` через `command_queue`, но **ActionMapper** его не использует — в проде работает прямой `send_data` из `action_cmd.py`.
3. **`write_db_err_devices` / `write_db_err_timeout`:** в [action_db.py](../client/EventsSystem/action_db.py) зарегистрированы как заглушки (`lambda` + `logger`). Запись в таблицу `Error` и сценарии CBS для аппаратных сбоев нужно **реализовать** в рамках миграции или отдельным подэтапом.
4. **Реле замка:** сейчас только [screen_14_stockman.py](../client/GUI/screen_14_stockman.py) + GPIO; выдача с механикой не синхронизирована с `$LOCK`. После внедрения `$LOCK` на выдаче потребуется **политика**: отказ от дублирующего GPIO для той же двери или чёткое разделение «большая дверь / служебный доступ».

### 2.5. Модель ячейки

[Cell.py](../client/DB/Models/Cell.py): `number`, `description`, связи с группой/типом инструмента, `status_id`. **Полей координат в мм нет** — потребуется расширение схемы или внешний конфиг с FK по `number`/`id`.

## 3. Целевой Hardware API (этап 0 — эталон)

### 3.1. Команды RPi → ATmega

| Команда | Назначение |
|---------|------------|
| `$MOT1,x` … `$MOT5,x` | Позиция мотора 1–5 в мм. |
| `$ZERO` | Калибровка, сброс координат. |
| `$STOP` | Аварийная остановка. |
| `$MOTn_SPEED,x`, `$MOTn_BOOST,x` | Скорость и ускорение. |
| `$LOCK,ms` | Открытие замков на **ms** (fail-safe). |
| `$LOCK0` / `$LOCK1` | Принудительно открыть/закрыть замки. |
| `$LED,x` | Яркость основной ленты 0–255. |
| `$ALED,r,g,b` | RGB адресной ленты (если прошивка поддерживает). |
| `$SENS1` … `$SENS6` | Запрос состояния датчика. |
| **`$DISP,ms`** (требование к прошивке) | Отдельно от `$LOCK`: соленоид **малой дверцы выдачи**, см. этап 1. |

Формат отправки в коде: полезная нагрузка без ведущего `$` в аргументе `send_data` (как сейчас `"$" + str(data)`), т.е. `data="MOT1,500"` → `$MOT1,500\r\n`.

### 3.2. Ответы ATmega → RPi

| Ответ | Смысл |
|-------|--------|
| `OK` | Команда принята к исполнению (короткие операции). |
| `DONE` | Завершена длительная операция (`$MOT*`, `$ZERO`, …). |
| `ERROR` | Ошибка параметра, концевик, таймаут и т.д. |
| `SENSx_0` / `SENSx_1` | Состояние датчика (разомкнут / замкнут). |

**Соглашение для Python:** нормализовать регистр при парсинге (`ok`/`OK`), не смешивать с устаревшими `command_ok` без моста совместимости.

## 4. Этап 1 — Прошивка ATmega (исполнитель: Федя)

Задачи из вашего плана дополняются критериями приёмки для Python-стороны.

| Задача | Критерий для клиента |
|--------|----------------------|
| Синхронизация оси Z (два мотора) | После `$ZERO` портал без перекоса; при необходимости плата выравнивает по нижним датчикам — иначе на RPi придётся дублировать логику (нежелательно). |
| `$STOP` во время `$MOT` | Прерывание `run()`-циклов; RPi может слать `$STOP` при смене экрана / таймауте; ожидается предсказуемый `OK` или `ERROR` + остановка. |
| `$DISP,ms` | Отдельная команда от `$LOCK`; иначе сценарий выдачи на RPi не сможет независимо управлять дверцей люка. |
| Единый формат ответов | Одна строка на событие, завершение `\n`; без «склеенных» двух ответов в одном чтении без разделителей (или буферизация на RPi с разбором по строкам). |

**Выход этапа 1:** стабильная прошивка + краткий «протокольный changelog» (что именно шлёт плата в пограничных случаях: два `DONE` подряд, `ERROR` после частичного хода и т.д.).

## 5. Этап 2 — Коммуникационный драйвер Python (исполнитель: Тимур)

### 5.1. Новый модуль vs доработка `serial_manager.py`

**Рекомендация:** ввести отдельный класс (условно `VendingSerialManager` или `HardwareLineProtocol`) в `client/BarcodeScanner/`, а **сканер** оставить на текущем `SerialManager` **или** вынести сканер в `BarcodeSerialManager` с построчным парсингом текста без `$`. Цель — не ломать эвристику `$…\n` для сканера, если он когда-либо попадает в тот же класс.

Минимальные требования к драйверу контроллера:

1. **Построчный парсер** (`readline` или накопление буфера до `\n`), учёт `\r\n`.
2. **Сигналы Qt (не блокировать GUI):**
   - либо один `pyqtSignal(str)` с каноническими именами (`hw_ok`, `hw_done`, `hw_error`, `hw_sens`, payload),
   - либо несколько сигналов (`line_received`, `done_received`, …).
3. **Очередь команд на запись** в том же потоке, что и чтение (устранение гонок с `send_data` из GUI).
4. **API отправки:** `enqueue_command("MOT1,500")`, `enqueue_command("ZERO")` и т.д. (без дублирования `$` в вызывающем коде — см. текущий `send_data`).

### 5.2. Менеджер очереди высокого уровня (логика «не шлём MOT5 раньше времени»)

Отдельный компонент (например `DispenseCommandGate` или часть будущего `action_dispense`):

- Состояние: «ожидаем `DONE` для оси X», «для Z», «можно MOT5».
- Вход: команды от сценария выдачи; выход: команды в `VendingSerialManager`.
- Обработка входящих строк: при `ERROR` — сброс gate и сигнал наверх в FSM/секвенсор.

Это **не** замена внутренней очереди потока COM, а **политика** поверх неё.

### 5.3. Mock

Переписать [MockSerialManager.py](../client/BarcodeScanner/MockSerialManager.py):

| Вход (после `$`) | Поведение мока |
|------------------|----------------|
| `LOCK,15000` | Сразу `OK` (или эквивалентный сигнал); в фоне `sleep(15)`; опционально сигнал «lock_released» только для отладки UI (на железе события нет — таймер только на RPi). |
| `MOT1,500` (и аналоги) | `OK`, пауза ~1–2 с, `DONE`. |
| `ZERO` | `OK`, пауза, `DONE`. |
| `SENS3` | через короткую задержку строка `SENS3_0` или `_1` (настраиваемо). |
| `ERROR`-сценарий | тестовая команда, например `MOCKFAIL`, чтобы отладить ветку «Сбой механики». |

Мок должен использовать ту же очередь/поток, что и реальный драйвер, чтобы не блокировать GUI.

### 5.4. Интеграция в `main.py` / Executor

- Подменить `controller_serial_manager` на новый класс при флаге конфига, например `"hardware": {"protocol": "atmega_hal_v1"}` или переменная окружения.
- `Executor.attach_serial_manager` подключать к **новым** сигналам; `handle_serial_controller` (MainWindow) вместо прямого `button_clicked(response)` для каждой строки — маршрутизация в **HardwareController** / секвенсор выдачи (см. этап 3).

## 6. Этап 3 — Бизнес-логика и кинематика на RPi

### 6.1. БД: координаты ячеек

**Вариант A (предпочтительно):** поля в `Cell`:

- `pos_x_mm` (int), `pos_z_mm` (int) — или `Float`, если прошивка допускает дроби.

**Вариант B:** JSON/YAML в ресурсах клиента + миграция только при отсутствии записи в БД.

**Миграция данных:** однократный скрипт (внутри проекта или админ-действие), импортирующий значения из [COORD.h](../client/Arduino/step_contioller/COORD.h) в поля по индексу ячейки; после проверки на стенде — ручная подстройка с инженерного экрана.

**CRUD:** расширить [CellCRUD.py](../client/DB/Engine/CellCRUD.py) и места выборки ячейки в [action_db.py](../client/EventsSystem/action_db.py) (`read_db_get_cell`, `read_db_get_more_cells`), чтобы в контекст выдачи попадали `pos_x_mm`/`pos_z_mm` (не только `number`).

### 6.2. Инициализация при старте (`$ZERO`)

Требование: на `screen_1_welcome` / `screen_32_wait` (или отдельный **`screen_hw_init`**), до разрешения логина — выполнить `$ZERO`, дождаться `DONE`.

**Реализация:**

- При первом показе приветствия или в `cmd_start` / `read_cnf_signature` цепочке запустить **HardwareInitController**:
  - если уже откалибровано в сессии — пропуск;
  - иначе отправить `ZERO`, показать полноэкранный «Калибровка…» или блокировать кнопку «Войти» до `DONE`;
  - при `ERROR` — экран критической ошибки + запись в `Error` + опционально `err_critical`.

Требуются новые переходы в [state_map.py](../client/StateMachine/state_map.py) и, при необходимости, новый экран UI.

### 6.3. Сценарий выдачи (sequence)

Вынести в отдельный модуль (например `EventsSystem/action_dispense.py` или `Hardware/dispense_sequence.py`):

Упорядоченные шаги (как в вашем ТЗ, с привязкой к протоколу):

1. `$ALED,255,165,0` — ожидание `OK` (или без ожидания, если плата не шлёт `OK` на короткие команды — уточнить по прошивке).
2. Параллельно или последовательно: `$MOT[X],coord_x` и `$MOT[Z],coord_z` — дождаться **`DONE` для обоих** (если команды асинхронны на плате, на RPi вести счётчик ожидаемых `DONE`).
3. `$MOT5,55` → `DONE` → `$MOT5,0` → `DONE`.
4. Парковка: `$MOT…,0` или `$ZERO` → `DONE` (политика на согласование с Федей: частый `$ZERO` изнашивает механику).
5. `$LOCK,15000` — после `OK` считать замок открытым на стороне контроллера на 15 с.

**Списание в БД:** перенести с события `command_ok` на **логическое завершение UX-таймера** (см. ниже), а не на первый `DONE` после толкателя.

### 6.4. Изменение FSM (два подхода)

**Подход 1 (рекомендуемый):** «толстый» секвенсор + «тонкий» FSM.

- Состояния FSM: `dispense_running` (один экран ожидания), `dispense_success`, `dispense_error`.
- Все подшаги MOT/LOCK — внутри Python-объекта с колбэками на сигналы драйвера.
- Триггеры в FSM: `hw_dispense_complete`, `hw_dispense_error`, `hw_dispense_timeout`.

**Подход 2:** расширить `state_map.py` десятками псевдосостояний под каждый шаг — **не рекомендуется** (сложность сопровождения).

### 6.5. UI-таймер и списание

Текущая цепочка: `command_ok` → `write_db_tool_consumption` → `screen_11_tool_issued`.

**Целевая цепочка:**

1. По завершении механики до шага `$LOCK,15000` перейти на `screen_11_tool_issued` (или остаться на анимации до открытия люка — UX-решение).
2. Сразу после успешной отправки `$LOCK,15000` запустить **QTimer на 15000 ms** для визуала «заберите инструмент».
3. По истечении таймера: вызвать логику **списания** (текущий `write_db_tool_consumption`), вернуть индикацию (`$ALED` / `$LED` — «красный» режим ожидания по ТЗ).

**Важно:** списание **не** привязывать к моменту закрытия замка на плате; оно привязано к **договорённому UX-времени**, синхронизированному с `$LOCK,ms` (одинаковые ms в команде и в QTimer).

### 6.6. Обработка `ERROR`

- Прервать секвенсор, не вызывать `write_db_tool_consumption`.
- Записать событие в [Error](../client/DB/Models/Error.py) через [EngineError](../client/DB/Engine/ErrorsCRUD.py) (тип, например `mechanics`, сообщение — сырой контекст последних команд).
- Перевести UI на экран «Сбой механики»:
  - либо новый `screen_mechanics_err`,
  - либо расширить [screen_12_no_tool](../client/GUI/screen_12_no_tool.py) / отдельный виджет текста ошибки.
- Добавить переходы из состояния выдачи по триггеру `hw_error` / `err_mechanics`.

Параллельно **реализовать** `write_db_err_devices` и `write_db_err_timeout` (сейчас заглушки в `action_db.py`), чтобы история ошибок попадала в CBS через существующий sync.

## 7. Этап 4 — Интерфейс и инженерное меню

### 7.1. Админ: `screen_26_admin` или `screen_hardware_test`

- Слайдеры/поля: `MOTn_SPEED`, `MOTn_BOOST` — отправка строк на контроллер.
- Jog: кнопки +10 / −10 мм для выбранной оси (`$MOTn,current±10` — текущие координаты хранит либо RPi, либо только плата; если только плата — нужен запрос позиции в протоколе **или** ведение «мягкой» копии на RPi после каждого `DONE` — **задание на уточнение в протоколе**, например `$POS?` → `MOT1_123`).
- Опрос `$SENS1`…`$SENS6` с индикацией (зелёный/серый) по ответу `SENSx_y`.
- Кнопка «Сохранить текущие X/Z в ячейку №…»: ручной ввод номера ячейки, запись в БД (и опционально вывод предупреждения, если каретка не совпадает с физическим люком — будущий контроль).

### 7.2. Экран кладовщика и GPIO

Согласовать с внедрением `$LOCK`:

- Если замок большой двери переведён полностью на ATmega — **убрать или отключить** `RelayWorker` для того же замка, чтобы не было двойного управления.
- Если реле остаётся для другого контура — задокументировать разделение.

## 9. Риски и смягчение

| Риск | Мера |
|------|------|
| Рассинхрон нескольких ожидаемых `DONE` | Явная машина состояний ожидания; таймаут шага + `$STOP` + переход в ошибку. |
| Частичные строки в буфере | Построчный парсер; не использовать `read_all()` для протокола текста. |
| Сканер и контроллер в одном классе | Разделить классы портов или строго разнести порты и парсеры. |
| Долгая калибровка при каждом старте | Кэш «калибровка ОК» с инвалидацией по `$STOP`/питанию — опционально, по решению техбезопасности. |

## 10. Критерии готовности (Definition of Done)

- На моках полный сценарий выдачи проходит без Arduino, включая задержку `$LOCK`.
- На стенде: выдача по ячейке из БД с координатами в мм; при `ERROR` инструмент не списывается, запись в `Error` создаётся.
- После перезапуска приложения выполняется политика `$ZERO` до входа пользователя (или осознанный skip с логированием).
- Инженерный экран позволяет настроить скорость/ускорение и проверить датчики.
- Документация в `docs/` отражает фактический протокол.
